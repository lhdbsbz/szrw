# contracts —— 项目自己的口径守卫

框架 §9 的验收里有 `go test ./contracts`：**生成器拦不住的项目约定**放这里。

生成器只查 proto 的机械规则（目录布局 / import 方向 / HTTP 路由 / 整数宽度），
「实体 ID 必须是 int64」「列表必须用 `common.PageInfoReq`」「某客户端的字段只许加」
这类是项目口径，只能靠测试守。

## 模板自带的一条

`proto_ids_test.go`：`proto/**` 里 `id` 与 `*Id` 字段只能是 `int64`。

理由见框架 §5：protojson 把 int64 编成十进制字符串，ts-proto 再收窄成 `EntityId`；
写成 `string orderId` 就悄悄回到「字符串当业务 ID」的旧世界（前端比较/精度都出问题）。
本来就该是 string 的外部标识与不透明句柄（渠道单号、SSO `clientId`、`traceId`…）
在 `stringIDAllow` 里登记理由——加一条等于一次评审。

守卫遍历 `../proto`，一个文件都没扫到会自己失败：目录改名比漏检更容易发生。

## 项目在这里加自己的

- 一条守卫只回答一个问题；失败信息写清「哪个文件 + 应该怎么改」，不要只说结论。
- 例外一律用 allowlist + 理由（`map[字段]理由`），不做「跳过这个目录」。
- 不要重复生成器的规则（布局 / import 方向 / 路径 / 整数宽度）：那些在
  `./scripts/gen.ps1` 阶段就失败了，写第二遍只会让两边说法慢慢分叉。
- 最值钱的守卫守的是「会腐烂的事实」：文档里写的仓库路径是否存在、主键是否雪花、
  已发布客户端的字段有没有被删改。
